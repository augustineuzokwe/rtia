## 0. How to read this audit

This is the first deliverable in a 3-PR robustness pass triggered by the
sequence #170 → #176 → #178 - three reactive fixes, each surfacing the next
bug. The stated goal: stop reactive patching, write down the contract, then
fix what writing it down reveals.

The audit is structured as:

1. **The components and panels** - every visible affordance and its purpose.
2. **State × panel visibility matrix** - for each `ThreadStatus`, what shows.
3. **State × button availability matrix** - for each `ThreadStatus`, what's clickable.
4. **Button → handler → API mapping** - drift surface area.
5. **Recovery paths** - what the user can do from each state.
6. **Honest bug list** - what this audit actually found wrong.
7. **Remaining risks** - things that smell like a future #170/#176/#178.

Empty cells in a table mean "not visible / not applicable" - explicit, not implied.

### Notes on the matrix

- **`(start, no run yet)` column** - the UI's initial render uses Gradio
  defaults (`visible=False` on every gated panel). There is no `IDLE` value
  in `ThreadStatus`; the closest is `_IdleState` (lines 660–668), which is
  used only inside `on_run` when the user clicks Run with empty text. It has
  `status = ThreadStatus.RUNNING` (sic - see [bug #2 below](#62-_idlestatestatus-is-running)).
- **`RUNNING` column** - `_state_to_panels` has **no explicit `RUNNING`
  branch**. RUNNING state hits the `base` defaults at lines 113–135, which
  hide every gated panel. This is correct for a transient state but means
  any future "show a spinner / progress UI" affordance will need an explicit
  branch.
- **`PAUSED_PO` deep vs split** - same panel visibility, but
  `po_split_checkboxes` is hidden in deep mode and shown in split mode
  (line 168 vs 184). `po_answers` is hidden in split mode when there are
  zero non-story questions (line 175).
- **`ERROR` row** - `result_visible=True` is set at line 253. Because the
  shared "Backlog target" group lives **inside** `result_panel` (lines
  330–350), it becomes visible too, with no values that make sense to act
  on. There is also no error-specific affordance (no "Try again", no link
  back to input). **This is the regression #186 flags.**

|---|---|---|---|---|---|---|---|---|

### Notes

- **`run_btn` is always clickable.** Clicking mid-pipeline (`RUNNING`,
  paused, done) **starts a fresh thread** - see `on_run` at lines 443–447,
  which calls `runner.start(text)` unconditionally. The old thread is
  effectively orphaned (still in the checkpointer; just not reachable from
  this UI session). The Gradio `thread_id_state` is overwritten on the next
  `_spread`. This is the only de-facto "reset" mechanism in the UI and is
  not documented anywhere visible to the user.

| `export_deferred_btn` | `on_export_deferred` (line 564) → `_select_followup_source` (line 45) → loops creating issues | `POST /pipeline/{thread_id}/export-deferred` | ⚠️ heavily duplicated - UI re-implements DONE_SPLIT vs DONE dispatch, `ExportTarget` construction, per-story loop. | `upload_pdf_input.change` | `on_upload_pdf` (line 418) → `extract_pdf(bytes)` directly | `POST /uploads/pdf` | ⚠️ UI bypasses API entirely; behavioral output is the same but error paths diverge (UI returns inline message; API returns HTTP status codes) |
| `upload_md_input.change` | `on_upload_md` (line 430) → `extract_markdown(bytes)` directly | `POST /uploads/markdown` | ⚠️ same as above |

### What the drift actually means

The pattern across every handler is: **the UI calls into shared helpers
(`PipelineRunner`, exporters, parsers) directly instead of going through
the FastAPI route layer**. The API and UI therefore share the *bottom*
of the stack but each implement the dispatch, error mapping, and request
shaping on top of it.

Concrete drift consequences observable today:

1. **`_resume_value_from` (api/main.py:122)** is the canonical resume-value
   builder. The UI doesn't use it - it builds the resume dict three
   different ways across three handlers. When a new resume shape is added
   (e.g. a future "skip this story" button at the review checkpoint), the
   API gets one update and the UI silently keeps building the old shape.
2. **`_build_deferred_followup_markdown` vs `_build_followup_markdown`** -
   two files, identical purpose, deliberately kept separate. If the
   provenance copy changes in one, the other rots.
3. **DONE_SPLIT dispatch** - both `api.main.export_deferred` and
   `ui.gradio_app.on_export_deferred` branch on `state.status ==
   DONE_SPLIT` to pick which list to iterate. Two parallel implementations
   of the same business rule.
4. **Error handling** - API maps `ExportConfigError → 400`,
   `ExporterTransportError → 502`. UI maps both to `"❌ <msg>"` inline.
   The UI surface is more forgiving but less informative.

## 5. The `outputs` tuple ↔ `_spread` alignment

The render contract is a 16-tuple. Defined twice:

- Construction: `_spread` (line 378) builds the tuple from the
  `_state_to_panels` dict.
- Wiring: `outputs` list (line 399) names the Gradio components in
  matching positional order.

Length: both **16 elements**. Positional alignment is by convention only -
there is **no assertion** that `len(outputs) == len(_spread(...))` and no
test that the keys in `_state_to_panels` line up with the
positional reads in `_spread`. A future contributor adding a new panel can
add it to `_spread`, forget to add it to `outputs` (or vice versa), and the
mismatch will manifest as a silent UI bug - the wrong component receives
the wrong update.

`_state_to_panels` also has keys that look unused at first glance:

| Key | Read by `_spread`? | Used? |
|---|---|---|
| `status_md` | ✅ | ✅ |
| `thread_id_state` | ✅ | ✅ |
| `po_visible` | ✅ | ✅ |
| `po_questions` | ✅ | ✅ |
| `po_split_checkboxes` | ✅ | ✅ |
| `po_answers_visible` | ✅ | ✅ |
| `po_split_visible` | ❌ | **unused - dead key** |
| `po_paused_payload` | ✅ | ✅ |
| `review_visible` | ✅ | ✅ |
| `review_preview` | ✅ | ✅ |
| `result_visible` | ✅ | ✅ |
| `result_md` | ✅ | ✅ |
| `download_file` | ✅ | ✅ |
| `deep_export_visible` | ✅ | ✅ |
| `deferred_visible` | ✅ | ✅ |
| `deferred_md` | ✅ | ✅ |
| `deferred_checkboxes` | ✅ | ✅ |
| `deferred_titles` | ❌ | **unused - dead key (set on lines 134, 206; never read)** |

Two unused dict keys carrying no signal. They suggest a prior intent (a
separate visibility flag for the split checkboxes; a titles list for some
downstream consumer that was never wired up) and they're load-bearing for
nothing today - pure noise. Removing them is a PR 2 candidate.

## 6. Honest bug list

### 6.1 `ERROR` state shows the "Backlog target" group

**Where:** lines 251–254 (the `ERROR` branch of `_state_to_panels`).
**Symptom:** when the pipeline errors, the user sees:

- An error message in `result_md` (✅ correct).
- The `download_file` slot (hidden - defaults to `visible=False`, correct).
- **The "Backlog target" form** (Backend / Target / Optional epic-or-project /
  Dry-run checkbox) - visible, with no way to act on it, because the deep
  export panel is hidden and so is the deferred panel. The user can type into
  fields that connect to nothing reachable.

**Why:** the Backlog target group (lines 330–350) is structurally a child
of `result_panel`. There is no separate `backlog_target_visible` flag.
When `result_visible=True` on ERROR (because we want to render the error
message in `result_md`), the entire `result_panel` subtree shows.

**Fix shape (PR 2):** either
(a) move the Backlog target group out of `result_panel` and give it its own
visibility flag (parallel to `deep_export_visible`), so it can be hidden on
ERROR while `result_md` is still shown; or
(b) move the error message out of `result_panel` into its own
`error_panel`, so `result_panel` only shows on `DONE` / `DONE_SPLIT`.

(b) is the cleaner separation given that ERROR has nothing else in common
with the success terminals.

### 6.2 `_IdleState.status` is `RUNNING`

**Where:** lines 660–668.
**Symptom:** the class is named `_IdleState` and used as the "no
requirement text submitted yet" placeholder, but its `status` attribute is
`ThreadStatus.RUNNING`. The comment ("the panels treat anything non-paused
as idle") explains the behavior, but the naming is actively misleading -
reading `_state_to_panels` with this object passed in, you'd reasonably
expect the `RUNNING` branch to fire (it doesn't exist; falls through to
base defaults).

**Impact today:** none observable - the base defaults happen to be the
right rendering for "idle". But the next person to add a `RUNNING` branch
to `_state_to_panels` (e.g. a spinner) will accidentally trigger it on the
empty-text path.

**Fix shape (PR 2):** add `IDLE = "idle"` to `ThreadStatus` (or use a
sentinel that doesn't pretend to be a real status) and rename the path.

### 6.3 No in-state retry from `ERROR`

**Where:** lines 251–254 and the absence of any retry affordance.
**Symptom:** from `ERROR`, the only path forward is: re-edit the textarea
(if the original input is even still there - it should be, since `req_text`
isn't cleared), click `Run pipeline` again. This starts a brand-new thread.
The old errored thread is orphaned.

**Why this matters:** for transient errors (a Gemini 503 on a single agent
call, a flaky exporter HTTP timeout), the user has to either retry the
entire pipeline from scratch (re-paying for analyst/PO/etc.) or know to
hit the CLI / API to resume. Neither is signposted in the UI.

**Fix shape (PR 2):** controversial - depends on whether the LangGraph
checkpointer can resume from ERROR. If yes, add a "Retry from last
checkpoint" button. If no, at minimum add a copy-pastable error trace so
the user can file an issue without re-running.

### 6.4 `run_btn` is a hidden reset button

**Where:** lines 443–447 (`on_run`).
**Symptom:** clicking Run mid-paused-pipeline orphans the current thread.
There is no confirmation, no warning, no visible reset path. The user who
accidentally clicks Run while at `PAUSED_PO` loses any context they'd
been editing into `po_answers`.

**Fix shape (PR 2):** either disable `run_btn` when a thread is active
(`status in {RUNNING, PAUSED_PO, PAUSED_REVIEW}`), or rename it to "Start
new run" and add a confirm dialog. The disable path is cleaner; the rename
path is more flexible.

### 6.5 Dead dict keys in `_state_to_panels`

**Where:** `po_split_visible` (set at lines 125, 168, 184; never read in
`_spread`); `deferred_titles` (set at lines 134, 206; never read).

**Impact today:** none observable. Pure noise.

**Fix shape (PR 2):** delete.

### 6.6 `on_review_override` does not validate input shape

**Where:** lines 494–499. Passes whatever's in the override textboxes
through unchanged. If the user submits both fields empty, the resume value
is `{"accepted": False, "description": "", "objective": ""}` - the graph
receives an override with no actual overrides. Likely benign (the
Story Writer / Composer should fall back to the existing values), but the
contract isn't enforced anywhere visible.

**Severity:** low. Flagged for completeness, not as something to fix in
PR 2 unless the graph mishandles it.

### 6.7 `download_file` writes to a tempfile that never gets cleaned up

**Where:** lines 196–202. Each render of the `DONE` state writes a fresh
`NamedTemporaryFile(delete=False, …)` and never cleans it up. Over a long
session this accumulates `.md` files in `$TMPDIR`.

**Severity:** low (OS cleans `$TMPDIR` on reboot). Worth a note for PR 2
because the obvious fix is to use the API's `/export.md` endpoint instead
(which streams the file directly with a `Content-Disposition`
attachment header - no temp file needed).

### 6.8 Symmetry mismatch: `on_export` vs `on_export_deferred` empty-thread guard

**Where:** `on_export_deferred` has a defensive `if not thread_id.strip()`
check at line 577 ("No active thread - start a pipeline run first.").
`on_export` (line 503) does not have the equivalent - it falls through to
`runner.get_artifact_and_title(thread_id)` which returns `None` for an
empty id, surfacing as "No final artifact for this thread yet."

**Impact today:** the user-visible message in the empty-thread case is
misleading on the deep export path but accurate on the deferred path. Same
underlying condition, two different messages.

**Severity:** low. Worth aligning in PR 2.

## 7. Recovery paths from each state

| From state | Available recovery actions |
|---|---|
| `(start)` | Paste text or upload a file; click Run. |
| `RUNNING` | Wait. (Run button is clickable but orphans the thread - bug #6.4.) |
| `PAUSED_PO` (deep) | Fill answers, click Submit. **No "skip this checkpoint" affordance.** Clicking Run starts over. |
| `PAUSED_PO` (split) | Adjust checkboxes (optionally), click Submit. |
| `PAUSED_REVIEW` | Accept, Override (with optional new description/objective), or click Run to restart. |
| `DONE` | View artifact, download .md, push to backlog (single artifact) or create follow-up issues (deferred batch), or click Run for a new requirement. |
| `DONE_SPLIT` | Create follow-up issues for the placeholders, or click Run for a new requirement. **Cannot drill into a placeholder from the UI** - user has to copy the title and re-paste as a new run. |
| `ERROR` | Re-edit input, click Run. **No retry from checkpoint, no error-trace copy, no "report this" link.** |

The most striking gap is `ERROR` (covered by bugs #6.1 and #6.3). The
second is `DONE_SPLIT` having no in-place "drill into this placeholder" button -
the docstring tells the user to re-run RTIA on the title, but the UI gives
no shortcut for it. Not a bug per se (the docs are honest about the
intended flow), but a friction point.

## 8. Remaining risks - things that smell like a future #170/#176/#178

These are the spots most likely to produce the next reactive fix. Ordered
by likelihood-of-pain × cost-of-fix.

### R1. The 16-element `_spread` ↔ `outputs` positional contract is unguarded

Every new panel or every removed panel touches two synchronized lists.
There's no test that catches a misalignment; in Gradio, the failure mode is
that the wrong component receives the wrong update - the UI looks subtly
wrong without an error.

**Mitigation in PR 2:** convert the return value of `_spread` to use a
dict + dispatch by component reference, or add a unit test that fixes the
key ordering. The dict approach is more idiomatic for newer Gradio versions
that accept dict returns.

### R2. Six handlers, all duplicating dispatch logic that lives in the API

Every UI handler is a parallel implementation of an API endpoint. The
docstring at `_build_followup_markdown` explicitly acknowledges this and
calls out a circular-import concern as the reason. Today there are 6
duplications; the trend has been monotonic upward (Phase 14 had 4; Phase
15 added 2; Phase 16 added the `_select_followup_source` helper to dedupe
*within the UI side only*).

The next API change to any of these endpoints will require a parallel UI
change. PR #170 was exactly this pattern (the API's `export-deferred`
endpoint added DONE_SPLIT dispatch; the UI button kept dispatching to the
deferred-only source and silently produced empty exports for split
threads).

**Mitigation in PR 2 (the drift-reduction PR):** call the API from the UI
in-process. This is what Gradio's `gr.Request` is for. The "circular
import" concern from the `_build_followup_markdown` docstring can be
resolved by extracting the shared helpers to a third module (`api/_shared.py`
or similar) that both `api/main.py` and `ui/gradio_app.py` import - no
circular dependency.

### R3. The "Backlog target" group has no visibility flag of its own

It inherits from `result_panel`. PR #178 added a separate
`deep_export_visible` flag for the deep export button group; the Backlog
target form (the inputs that drive both exports) was left without one.
This is the proximate cause of bug #6.1 and will be the cause of any
future bug that needs "show the export inputs but not on this state".

**Mitigation in PR 2:** either pull the Backlog target group out of
`result_panel` and give it its own flag, or split `result_panel` per
status.

### R4. `_state_to_panels` has no explicit `RUNNING` branch

This is fine for now - the base defaults render "everything hidden", which
is what we want for a transient state. But the panel-fallthrough behavior
combined with `_IdleState.status = RUNNING` means the day someone adds a
RUNNING branch (e.g. "show a spinner"), the empty-input path will
accidentally trigger it.

**Mitigation in PR 2:** introduce a real `IDLE` sentinel (see bug #6.2)
and treat `RUNNING` as a first-class branch with no UI affordances yet.

### R5. Pipeline-state mutation from the UI bypasses API validation

`runner.start()`, `runner.resume()`, `runner.get_state()` are called
directly. The API layer wraps them with `InvalidUpdateError → 400`
mapping. The UI doesn't. A LangGraph state-update failure surfaces as an
uncaught exception in a Gradio handler - Gradio will render a generic
error toast, but the user has no way to recover (no `thread_id` is
preserved if the exception fires before `_spread`).

**Mitigation in PR 2:** at minimum, wrap every runner call in a
try/except that produces a meaningful `_state_to_panels`-shaped ERROR
state.

### R6. No state machine assertion

There is no place in the codebase that says "PAUSED_PO can only
transition to PAUSED_REVIEW or DONE_SPLIT or ERROR". `_state_to_panels`
trusts whatever `state.status` it sees. If a graph change adds a new
status, the UI silently falls through to base defaults - every panel
hidden - and the user sees only `status_md` updating with no idea what to
do.

**Mitigation in PR 2:** add an explicit `else` branch that renders a
"Unknown state - please report this" message with the status value, so
new statuses fail loud.

### R7. `req_text` is never cleared

Across runs, the textarea keeps whatever the user pasted. This is
arguably a feature (preserves work on error). But combined with the
"Run button orphans threads" footgun (R8 = bug #6.4), it means a user can
end up running the same input twice without realizing.

**Mitigation in PR 2:** debatable. Probably leave it but add a "Clear"
button, or pre-fill `req_text` with `""` only after a successful `DONE` /
`DONE_SPLIT`.
